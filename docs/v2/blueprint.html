Adapt 2.0 · product blueprint

An engine that learns a person,
and knows when it doesn't.

Adapt decides what a person should do next, and tells you how sure it is — or abstains and says what it would need to know. Hosts embed it through an API. We sell the institution access to an engine we keep maintaining, not tokens and not coverage.

Three things that must never be confused

Every capability is described on three separate axes, each on the same L0–L3 scale. What a customer actually receives is the minimum of the three, and the binding constraint is always named in the response.

Entitlement
Have they bought it?
Commercial. Set by contract and tier.
Capability
Have we built it?
Engineering. Set by the release.
Validation
Have we earned the claim?
Evidence. Set by the gates, on their own learners.

A tenant can own Deep and still be served L1 with limited_by: "validation", because their learners have not accumulated the evidence yet. That is the difference between selling a capability and overstating one.

The loop

Host product
“What should this person do next?” — asked with a learner id, a construct and whatever history exists.
⇄
Enough evidence?
If yes: serve a recommendation, with the interval that justifies it.
If no: abstain, name the reason, and say how many observations would change the answer.
Observe
The host reports what actually happened. The model gets sharper for that learner, that construct, that cohort.

Abstention is a feature, not a failure. A brand-new learner gets insufficient evidence plus the number of trials that would fix it — never a confident guess, never a canned default. It is never billed, at any tier, and never counted as an error.

But abstention alone can hide an empty product: a system that abstains on everything looks honest and serves nothing. So the headline metric is a pair — abstention rate and served rate, same screen, same denominator. Careful engine or unfinished engine; the pair is how you tell.

The pricing unit is a bundle, not a token: 80 credits ≈ one reference learner-month, priced from willingness to pay, operating cost and margin — never derived from compute. Monthly included allowance per tier, usage packs on top, no surprise overage, customer-set caps. Included allowances expire; purchased packs never do.

Foundations first is deliberate. Tenant isolation, an append-only ledger and encryption at rest are the three things that are ruinous to retrofit — a model built on a database that cannot prove who sees what is a demo, not a product.

What “done” means for a host

  • Under 15 minutes from docs to a first successful call — tested with a developer who has never seen them.
  • A demo they can watch: a learner with zero history abstains, earns its evidence in six interactions, then serves a recommendation with a visible interval. Nothing fabricated.
  • A conformance suite in their CI — 15 checks; the reference host scores 100% or the build fails.
  • Byte-identical replay of any decision, from its id.
