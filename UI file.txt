## PART 1 — What changed from the previous design pass, and why (read this before building)

A prior version of this redesign used a chrome-less shell with navigation hidden behind
a small corner tab that opened a full-screen index. **That pattern is cancelled.** It
made the app's own author unable to find Settings. Replace it with a **permanent,
always-visible left sidebar** containing every top-level destination, labeled in plain
words, with the current page always visually obvious. Discoverability beats originality
here — full stop. If anything else in this document seems to still imply hidden/
on-demand navigation, that's a leftover; the sidebar wins.

A prior version also had several controls (decision actions, nav-ish elements) styled as
plain colored/underlined text with no border or fill, making it unclear they were
interactive. **Fixed via a single explicit button system** (Part 2.2) that every
clickable control in the app must use. No exceptions for "but it looks cleaner as just
text" — if it does something, it must look like it does something.

Finally, the product now requires an explicit **consent-to-monitoring step** before
account creation (Part 2.4) — this is a new real screen, not a restyle of an existing
one, and needs an actual API field to persist it (flag this as a backend dependency,
see Part 1.1).

### 1.1 New dependency this introduces — flag, don't silently build around

The consent step's "I agree" / "I also agree to research use" state needs to be
persisted somewhere (ideally as part of account creation or `me/preferences`). **Check
whether the current API already has a field for this.** If it does not, this is new
backend scope outside a pure restyle — implement the consent *screen* and its local
gating logic now, but flag in your report that persisting the decision needs a new or
extended endpoint/field, and do not invent a client-only fake persistence for it (e.g.
don't silently only store it in `localStorage` and call it done — say plainly that it's
UI-only pending a real field).

### 2.2 THE BUTTON CONTRACT (mandatory, applies to every interactive control app-wide)

This is the single most important fix in this pass. Define three `Btn` visual variants
in `components/ui.tsx` (keep existing `tone`/`kind` props; this just changes which
variant each tone maps to and what the variant actually renders):

```tsx
// Primary — solid fill, highest-commitment actions (submit, agree & continue, start learning)
.btn-primary {
  background: var(--ink); color: var(--bg); border: 1.5px solid var(--ink);
  padding: 13px 24px; border-radius: 4px; font-family: var(--font-mono);
  font-size: 12px; text-transform: uppercase; letter-spacing: .05em; cursor: pointer;
}
.btn-primary:hover:not(:disabled) { background: var(--accent); border-color: var(--accent); transform: translateY(-1px); box-shadow: 0 3px 0 var(--line); }
.btn-primary:disabled { opacity: .35; cursor: not-allowed; }

// Secondary — bordered, filled background, mid-commitment actions (decisions, ratings, frame tabs)
.btn-secondary {
  background: var(--panel); color: var(--ink); border: 1.5px solid var(--line);
  padding: 11px 20px; border-radius: 4px; font-family: var(--font-mono);
  font-size: 11.5px; text-transform: uppercase; letter-spacing: .04em; cursor: pointer;
}
.btn-secondary:hover:not(:disabled) { border-color: var(--accent); color: var(--accent); }
.btn-secondary[aria-pressed="true"], .btn-secondary[aria-checked="true"] {
  background: var(--accent-dim); border-color: var(--accent); color: var(--accent); font-weight: 600;
}

// Ghost — real but low-commitment actions (skip, "not now", secondary links). STILL has a
// visible boundary — an underline is not enough on its own; pair with spacing/padding so
// it reads as a hit target, not a stray word in a sentence.
.btn-ghost {
  background: transparent; color: var(--muted); border: 1px solid transparent;
  padding: 10px 14px; font-family: var(--font-mono); font-size: 11px;
  text-transform: uppercase; letter-spacing: .04em; text-decoration: underline;
  text-underline-offset: 3px; cursor: pointer;
}
.btn-ghost:hover { color: var(--ink); border-color: var(--line); border-radius: 4px; }
```

**Rule**: a plain `<a>`-style inline text link (e.g., "Read the full privacy policy")
is the *only* exception allowed to look like plain underlined text with no padding/
border — because it navigates to reference material, not an action with a consequence.
Everything that submits, decides, rates, selects, or advances state uses one of the
three `.btn-*` classes above. Audit every screen in Part 3's table against this before
calling it done.

**Selectable options (MCQ answers, etc.) are not plain list items.** They need a
visible container (border, padding, background) and an explicit selection indicator
(a radio dot/checkbox glyph), not just a color change on the text:

```tsx
.option-card {
  display: flex; align-items: center; gap: 14px; width: 100%; text-align: left;
  padding: 14px 16px; border: 1.5px solid var(--line); border-radius: 4px;
  background: var(--panel); cursor: pointer; font-family: var(--font-sans); font-size: 15px;
}
.option-card:hover { border-color: var(--accent); }
.option-card[aria-checked="true"] { border-color: var(--accent); background: var(--accent-dim); font-weight: 600; }
.option-card .radio-dot {
  width: 16px; height: 16px; border-radius: 50%; border: 1.5px solid var(--line);
  flex-shrink: 0; display: flex; align-items: center; justify-content: center;
}
.option-card[aria-checked="true"] .radio-dot { border-color: var(--accent); }
.option-card[aria-checked="true"] .radio-dot::after {
  content: ''; width: 8px; height: 8px; border-radius: 50%; background: var(--accent);
}
```

### 2.4 New screen: consent — before account creation

New route or step in the existing auth flow (confirm with current `/` / onboarding
structure whether this is a new page or an early step inside onboarding/auth — place it
wherever account creation currently begins, but it must appear **before** any
account-creating API call, including the guest path if the guest path also creates a
student record per `POST /students`).

Required elements:
- Plain-language explanation of what's recorded (answers, response times, navigation
  through lessons) and why (personalizes the practice shown; may inform product
  improvements in de-identified, aggregate form).
- A **required** checkbox, unchecked by default: "I understand my learning activity is
  recorded and used to adapt what I'm shown."
- A **separate, optional** checkbox, unchecked by default: "I'm also willing to have my
  anonymized activity used for research to improve ADAPT for other learners." Must be
  genuinely separable from the required box — never bundle them into one checkbox, and
  never pre-check either.
- A real link to the full privacy policy (plain inline text link, the one allowed
  exception per 2.2).
- A `.btn-primary` "Agree & continue," disabled until the required box is checked.
- A `.btn-ghost` or clearly secondary "Decline" path that does **not** dead-end: show an
  honest `Notice` explaining what won't work without the required consent (e.g.
  personalized practice), consistent with rule 5 (honest fallbacks).

### 2.5 Home screen — status + one primary action, not a nav substitute

Home no longer tries to double as navigation (the sidebar's job now). Structure:
- Greeting + one `.btn-primary` "Continue practicing" (or "Start learning" for a new
  learner who hasn't begun) routing to `/learn`.
- A small set of real-data status cards (due for review, pending changes count, current
  band, streak if available) using actual values from existing reads (`dashboard`,
  `review/due`, `adaptations/pending`) — not placeholders, and not fabricated numbers if
  a given value isn't available from the current API for a given state (e.g., a brand
  new account has nothing due yet — show that honestly, not a zero dressed up as data).

### 2.6 `Band`, `Ledger`, `Receipt` — unchanged from prior spec

Keep the `Band` component's uncertainty-channel rule: only encode position/range/count
if the real API response actually provides that data (check `lib/types.ts` for
`dashboard`/`journey` shapes before committing to the three-channel encoding). Keep
`Ledger`/`LedgerEntry` and `Receipt` as additive exports per the earlier spec — same
code shape as before, just styled with the new button contract for their action rows.

### 2.7 Accessibility patterns — unchanged requirement, reuse across screens

Roving tabindex for option groups and filmstrip tabs, focus-trapped dialogs for any
modal that remains (e.g., a confirmation dialog, not the old nav overlay which no
longer exists), a shared `aria-live` region for state changes that were previously
silent (decision saved, answer graded, rating applied, consent recorded). Implement
once, reuse everywhere — same utility functions as previously specified
(`useRovingTabIndex`, `useFocusTrap`, `announce()`).

## PART 4 — Do / Do not (exhaustive)

### Do
- Make every clickable control pass this test: *could a first-time user tell, without
  hovering, that this is clickable?* If the answer requires hover to discover, it fails
  the button contract (Part 2.2) and must be fixed.
- Keep the sidebar visible and the current page marked (`aria-current="page"`, a
  distinct active style) on every single screen, with no exceptions.
- Treat the consent screen as mandatory in the account-creation path, including the
  guest path if it also creates a student record.
- Run the narrowest relevant probe scenario after every screen.
- Flag the consent-persistence backend gap explicitly rather than quietly faking
  storage for it.

### Do not
- Do not hide primary navigation behind a corner control, a hamburger-only pattern on
  desktop, or any "discover it" interaction model. Desktop always shows the sidebar.
- Do not style any state-changing control (submit, decide, rate, select, agree) as
  plain colored or underlined text with no border/fill/padding.
- Do not pre-check the optional research-consent checkbox, or bundle it with the
  required consent checkbox.
- Do not add a new `fetch()` call outside `lib/api.ts`'s existing wrappers.
- Do not fabricate uncertainty, evidence counts, or review-interval positions the real
  API doesn't provide.
- Do not let the homepage regain any "also serves as navigation" responsibility — the
  sidebar is the only navigation surface.
- Do not weaken or delete a probe assertion to force green; diagnose first.
- Do not reintroduce deficit language, trait labels, or a "learning style" concept
  anywhere.
- Do not claim accessibility or responsiveness as verified beyond what you actually
  implemented and could check in this environment — state the gap plainly.

    const y=24+i*laneH, cx=xOf(t.est), halfW=t.unc*300, r=6+Math.sqrt(t.n)*1.3;
    g.innerHTML += `<line x1="${cx-halfW}" y1="${y}" x2="${cx+halfW}" y2="${y}" stroke="var(--line)" stroke-width="2"/>
      <line x1="${cx}" y1="${y-6}" x2="${cx}" y2="${y+6}" stroke="var(--ink)" stroke-width="2"/>
      <circle cx="${cx}" cy="${y}" r="${r}" fill="var(--accent)" opacity="0.35" stroke="var(--accent)" stroke-width="1.5"/>
      <text x="4" y="${y-9}" font-family="JetBrains Mono" font-size="10.5" fill="var(--ink)">${t.name}</text>`;
    tbody.innerHTML += `<tr><td>${t.name}</td><td>${t.band}</td><td>${(t.est*100).toFixed(0)}%</td><td>±${(t.unc*100).toFixed(0)}</td><td>${t.n}</td></tr>`;
  });
}
